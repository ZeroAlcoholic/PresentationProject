企業 AI 工作轉型方法論

任何可以被規格化的工作
AI 就能可靠地協助執行

不只是工程師的程式碼——研究分析、法務文件、客服流程、行銷素材、HR 教材、主管決策——只要把工作寫成可執行的規格，AI 就能接手執行，人類保留判斷與驗收。

❌ 舊做法：模糊需求 → AI 猜測 → 反覆修改
「幫我做一個報表」→ AI 自由發揮→ 範疇不明→ 反覆修改，沒有驗收終點
✓ Spec-Driven：規格化 → AI 可靠執行 → 人工審核 → 可複用
Problem Spec→ Context + Output→ AI 執行→ Validation→ 人審核 → 複用 ✓
💡
核心論點

工程師最先用程式碼驗證了這件事。Spec-Driven Work 是把這套方法延伸到企業每個職能的方法論。

為何現在

AI 已從工具，進入工作流程本身

真正的轉變不是「AI 讓工作更快」，而是「工作的執行單位正在改變」——從人寫出來，到人規格化、AI 執行、人驗收。

「AI 是 放大器（amplifier）——它放大強流程，也放大弱流程。越早練會問題拆解、規格撰寫與驗收設計，越早把 AI 從個人工具升級成組織交付能力。」

方法框架

六層規格：把任何工作變成 AI 可執行的單元

Spec-Driven Work 的核心是一套六層結構。工程師叫它 SDD，非工程師叫它 SDW，本質相同：先把工作寫清楚，AI 才能可靠地執行，人才能有效地審核。

為什麼六層缺一不可：跳過 Problem 會讓 AI 解錯問題；跳過 Validation 無法交付；跳過 Human Review 失去判斷責任；跳過 Reuse 讓每次都從零開始。

方法框架

三個核心操作技巧

以工程任務為主要示例；括號內為非工程職能的對應做法。這三個技巧適用所有職能。

TECHNIQUE 01
三段式 Prompt 結構
分 Discovery / Planning / Execution 三段確認，每段完成後才繼續
Stage 1：「探索範疇，了解架構，不修改任何東西，列出疑問等確認。」
Stage 2：「根據 Spec 列出計畫，只列計畫，確認後再開始。」
Stage 3：「執行 T1，自行跑驗收，測試不過請修正後重跑，直到通過。」
TECHNIQUE 02
禁區設定（比目標更重要）
在 Spec 的 Non-goals 明確列出：「不包含 X、不修改 Y、不碰 Z」
在 Context 文件寫入全域禁止規則，讓 agent 在整個任務都知道不能碰什麼
Non-goals 範例：「不處理掃描圖片 PDF、不做 UI 重設計、不支援多物流商」
AI 預設行為是「幫你多做一點」。沒有明確禁區，它會越界越改越多。
TECHNIQUE 03
驗收優先設計
在開始前就寫好 Acceptance Criteria 與 Verify 指令，不等 AI 完成再想「要怎麼驗」
在 Prompt 明確要求：「完成後自己跑驗收，不過請修正後重跑」
Verify by（工程）：npm run test:pdf-accuracy -- --threshold=0.95
Verify by（法務）：法務主管抽驗 20 份，準確率須 ≥95%，每個風險標記必須附引文位置。
⚙️
核心邏輯

驗收標準是 AI 判斷「完成」的唯一依據。不事先定義，AI 會自我判斷「差不多了」——人也沒有客觀標準可以拒絕。

企業案例

六個典型案例：SDW 在各職能的落地

重點不是「他們用了 AI」，而是「他們如何把工作規格化」——哪些層次寫清楚了、驗收怎麼設計、哪些判斷保留人工。

Klarna客服
明定哪些客服場景可自助、哪些須升級人工，Context 限定核准知識庫範圍，Output 格式固定（回答＋升級標籤）。
SDW：Problem → Context（知識庫邊界）→ Output（回答＋標籤）→ Validation（誤答率門檻）
Morgan Stanley研究
每年從 70,000 份報告萃取洞察，Output 格式要求引文＋摘要分開，人工確認是對外發布的必要關卡。
SDW：Context（研究庫邊界）→ Output（引文＋摘要）→ Human Review（對外前確認）
Banesco USA法務
授信備忘錄從一週壓縮到數分鐘，每個環節輸出格式均先定義：文件上傳→萃取→draft→覆核。準確率提升 89%。
SDW：Output（備忘錄格式規格）→ Validation（準確率 +89%）→ Human Review（承作覆核必要）
Sami Saúde醫療
Output Spec 明定摘要結構與標籤規格；81% 摘要無需修改。醫師簽核是流程中不可省略的 Human Review。
SDW：Output（摘要格式）→ Validation（81% 無需修改，月省 900h）→ Human Review（醫師簽核，不可省）
Deutsche Bahn營運
先建 Context（平台規則、受管環境），再定義 Validation（上線條件審核）。4,000 名公民開發者上線 500+ 生產 apps。
SDW：Context（受管環境）→ Validation（上線審核）→ Reuse（CoE 模板庫）
Dunaway法規研究
Atlas 系統集中索引城市法規，Output 規格要求每個回答必須附引文段落；Reuse 設計自動同步法規更新。年省 1 萬小時。
SDW：Context（核准資料庫）→ Output（答案＋引文）→ Reuse（自動同步更新）
落地指南

各職能的能力重心上移

這不是「AI 取代員工」——而是工作重心從「執行層」上移到「定義層」。真正的能力升級是把工作拆得夠清楚，讓 AI 可以穩定接手執行的部分。

跨職能共同結論

無論哪個職能，能把問題定清楚、驗收設好的人，是 AI 時代最有槓桿的角色。執行本身越來越便宜，定義與驗收的能力越來越值錢。

導入路線

五步建立新型態工作模式

1
校準認知，對齊團隊

對齊誰負責定義問題、誰設計驗收標準、AI 在哪個環節介入

2
選擇試點：從容易量化的開始

高頻文件處理、知識檢索、決策摘要——輸入 / 輸出清楚、低風險可回滾

3
先規劃，先定義驗收

Non-goals 比 Goals 更難寫也更重要——先準備測試資料與 Acceptance Criteria

4
執行 + 把關風險

建立 Context 文件，明確禁止事項。AI 輸出當作草稿，關鍵業務邏輯人工確認

5
驗收交付 → 複製流程

整理 spec 格式、task 拆解、驗收清單為可複製模板，讓第二個問題成本大幅降低

🗺️
導入結論

新型態工作模式的核心習慣只有四個：先對齊、先規劃、訂立驗收、把關風險。前三個月先求一個試點跑通，建立信心與可複製的流程。

選對第一個試點的條件
✓ 輸入 / 輸出清楚
✓ 有測試資料可驗收
✓ 非安全關鍵決策
✓ 改壞了容易回滾
✓ 高頻、可量化效益
