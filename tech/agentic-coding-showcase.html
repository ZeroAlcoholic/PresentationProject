企業 AI 工作轉型方法論

任何可以被規格化的工作
AI 就能可靠地協助執行

不只是工程師的程式碼——研究分析、法務文件、客服流程、行銷素材、HR 教材、主管決策——
只要把工作寫成 可執行的規格，AI 就能接手執行，人類保留判斷與驗收。

核心論點：工程師最先發現這件事：當你給 AI 清楚的 spec，它能接手整個 repo-level 的工程任務。但這個邏輯不屬於工程師——它屬於所有人。 Spec-Driven Work 是把這套方法延伸到企業每個職能的方法論。
舊做法：模糊需求 → AI 猜測 → 結果不穩
「幫我做一個報表功能」→ AI 自由發揮→ 範疇不明→ 無驗收標準→ 反覆修改
Spec-Driven：規格化 → AI 可靠執行 → 人工審核 → 可複用
Problem Spec→ Context + Output→ AI 執行→ Validation→ 人審核 → 複用 ✓
為何現在

瓶頸從「誰來寫」變成「誰能把問題拆清楚」

AI 工具普及之後，大多數團隊的提效仍停在個人層次——更快打字、更快搜尋。真正的轉型在於：把「把工作交代清楚」這件事，從隱性技能變成可複製的組織流程。

「AI 是 放大器（amplifier）——它放大強流程，也放大弱流程。越早練會問題拆解、規格撰寫與驗收設計，越早把 AI 從個人工具升級成組織交付能力。」

核心洞察

工程師最先用程式碼驗證了這件事：清楚的規格讓 AI 可以接手整個任務。 現在這個邏輯正在擴散到每個職能。問題不是你在哪個部門，而是你能不能把工作寫成 AI 可執行的規格。

方法框架

六層規格：把任何工作變成 AI 可執行的單元

工程師叫它 SDD，非工程師叫它 SDW，本質相同——六層缺一不可。Problem → Context → Output → Validation → Human Review → Reuse：每一層解決一個「AI 失控的原因」，六層合在一起，才能讓任何工作的輸出品質可預測、可審核、可複用。

哪些決策必須人工判斷？誰負責最終確認？

非工程法律責任判斷、例外條款協商、簽核決策

這次產出能作為下次的起點嗎？
工程元件庫、spec 模板、驗收 checklist、prompt 範本
非工程標準合約範本、審查 SOP、AI workflow 模組
為什麼六層缺一不可：跳過 Problem 會讓 AI 解錯問題；跳過 Validation 無法交付；跳過 Human Review 失去判斷責任；跳過 Reuse 讓每次都從零開始。六層合在一起，才能把任何工作變成 AI 可重複執行的單元。

三個核心操作技巧

以工程任務為主要示例；括號內為非工程職能的對應做法。

TECHNIQUE 01
三段式 Prompt 結構
不要一次給一個大 Prompt——分 Discovery / Planning / Execution 三段確認，每段完成後才繼續
Stage 1（工程）：「請探索 repo，了解架構與測試框架，不修改任何檔案。列出疑問等確認。」
Stage 2（工程）：「根據以下 Spec 列出實作計畫。只列計畫，不實作，確認後再開始。」
Stage 3（工程）：「執行 T1。完成後自行跑驗收，測試不過請修正後重跑，直到通過。」
非工程例：「請讀取合約清單與審查重點，了解範疇，不開始審查，列出疑問後等確認 → 提出審查計畫等確認 → 執行首份審查並附引文，等確認後繼續下一份。」
一次一個段落確認，避免 AI 在未理解完整情境前越界操作，也讓人有機會在每個節點調整方向
TECHNIQUE 02
禁區設定（比目標更重要）
在 Spec 的 Non-goals 明確列出：「不包含 X、不修改 Y、不碰 Z」
在 CLAUDE.md 寫入全域禁止規則，讓 agent 在整個 repo 都知道不能碰什麼
在每個 Prompt 重申當前邊界：「只做 T1，不要主動修改其他模組」
Non-goals 範例：「不處理掃描圖片 PDF（手寫辨識排第二版）、不做 UI 重設計、不支援多物流商」
AI 預設行為是「幫你多做一點」。沒有明確禁區，它會越界越改越多——而且你通常不會馬上發現
TECHNIQUE 03
驗收優先設計
在開始前就寫好 Acceptance Criteria 與 Verify 指令，不等 AI 完成再想「要怎麼驗」
準備好測試資料（測試集、邊界條件樣本），讓驗收可以自動執行不依賴人眼
在 Prompt 明確要求：「完成後自己跑驗收指令，測試不過請分析原因並修正後重跑」
Verify by（工程）：npm run test:pdf-accuracy -- --threshold=0.95 && npx playwright test pdf-flow/
Verify by（法務）：法務主管抽驗 20 份，準確率須 ≥95%，每個風險標記必須附引文位置。
驗收標準是 AI 判斷「完成」的唯一依據。不事先定義，AI 會自我判斷「差不多了」——人也沒有客觀標準可以拒絕

⚙️
核心論點

SDD 不等於全部 Agentic Coding；SDD 是讓 Agentic Coding 變成企業可交付流程的核心方法。不是把 coding slice 丟給 AI，而是讓 AI agent 在明確規格與驗收標準下承接多步驟工程任務。

落地指南

從規格到交付：試點選擇、驗收設計、角色分工

SDW 的方法寫在框架裡，但真正落地需要三件事：選對第一個試點、建立可量化的驗收標準、讓每個角色找到新定位。以下是三套實戰指南。

01 · 六大驗收面向

任何 SDW 輸出，無論哪個職能，都要通過這六道驗收。這是從「能用」到「可靠交付」的差距。

1
輸出符合規格

符合 spec 中的 Output 定義，邊界條件正確處理，主要流程與異常路徑都有覆蓋。

✓ AC 驗收條件 100% 通過
2
資料與引用可信

輸入 / 輸出有量化指標，資料來源可追溯，引用完整，推論與事實分開標示。

✓ 準確率 / 引文完整率 ≥ 閾值
3
方法論可驗

AI 輸出的判斷方式透明，結果可重現，有 baseline 比較，能力邊界已知且已告知。

✓ 評估框架通過，邊界已明定
4
流程穩定可重跑

失敗有明確處理機制，不靜默失敗，重跑後輸出一致，可監控異常與延遲。

✓ 穩定性測試 / 監控到位
5
合規與治理

符合資安政策與法遵要求，敏感資料處理合規，存取控制正確，稽核軌跡完整。

✓ 資安 / 法遵 / 稽核確認
6
流程可移交

有文件、SOP、監控告警，後續人員可接手，不依賴特定個人，知識沉澱在流程中。

✓ Handoff Checklist 通過

02 · 六種適合起步的試點類型

選擇首個試點的關鍵：輸入 / 輸出清楚、有樣本可驗收、非高風險決策、做壞了容易更正。

📄

高頻文件 / 合約處理

合約審查、PDF 欄位萃取、申請書分類。I/O 最清楚、準確率最容易量化，任何職能都適合起步。

法務 / 客服 / 行政準確率驗收
🔍

知識檢索與研究摘要

從大量文件、報告、法規中找答案並結構化輸出。引用來源可驗，推論與事實分開。

研究 / 法務 / HR引文完整率
💬

客服知識流設計

把高頻問答轉為知識庫，設信心門檻與升級路徑。自助率、誤答率是明確的 Validation 指標。

客服 / 銷售自助率量化
📋

決策文件與週報生成

把分散資訊壓成一頁 memo 或週報，格式固定、數字可交叉核對，人工審最終版本。

主管 / PM / 財務格式固定驗收
🧪

結構化原型與假設測試

先寫 Problem Spec + Non-goals，用原型或多版本素材驗證假設，早期對齊後再投入開發。

PM / 行銷 / 產品假設驗證驅動
🔄

高頻行政流程自動化

資料格式轉換、報表整合、作業標準化。重複性高、輸出格式固定，最適合建立可重跑 workflow。

營運 / 行政 / 財務可重跑驗收

跨職能共同結論

無論哪個職能，能把問題定清楚、驗收設好的人，是 AI 時代最有槓桿的角色。執行本身越來越便宜，定義與驗收的能力越來越值錢。

導入路線

五步建立新型態工作模式

轉型不是一次性的工具學習，而是逐步建立的工作習慣。從第一個試點開始，讓每個步驟都有可驗收的成果。

1
校準認知，對齊團隊

這不是「讓 AI 幫你寫更多 code」，而是「讓部門能接住更大範圍的業務問題」。在開始前，讓所有相關人員對新工作方式有共識：誰負責定義問題、誰設計驗收標準、AI 在哪個環節介入、人在哪個環節把關。對齊步驟跳過，是導入失敗最常見的原因。

工作方式對齊先行角色分工說清楚人定義，AI 執行
2
選擇試點任務：從容易量化的開始

第一個試點最重要的任務是「讓流程跑通一次」，而不是選最複雜的問題。選符合條件的工作：輸入 / 輸出清楚、有測試資料、非安全關鍵、改壞了容易回滾。報表、文件處理、資料清洗是最適合的起點。

清楚 I/O有測試資料低風險可回滾
3
先規劃，先定義驗收

動手之前，先把問題寫清楚（SDD Spec），再定義「什麼算完成」（Acceptance Criteria）。Non-goals 比 Goals 更難寫，也更重要——它決定了範疇邊界，讓 AI 不會越界。Verification 指令要在動手前就設計好，測試資料也要事先準備。沒有 Spec、沒有 AC 就開始，是 AI 輸出偏離、大量重做的根本原因。

Non-goals 是護欄AC 要可量化先準備測試資料
4
執行 + 把關風險

先建立 Workflow Context 文件——工程任務稱 CLAUDE.md / AGENTS.md，其他職能是工作邊界 SOP 或 spec 說明（架構、慣例、禁止事項）——再把 spec 拆成 3–7 個可獨立驗收的任務。執行時，告訴 AI「不能做什麼」比告訴它「要做什麼」更重要——禁區設定是最容易被跳過的步驟。AI 輸出要當作草稿：關鍵數據人工抽驗、關鍵業務邏輯第二人確認、灰色判斷保留人工把關。

工作邊界文件先寫明確禁止事項交叉驗證關鍵輸出
5
驗收交付 → 複製流程 → 部門服務化

通過六大企業驗收面向後，試點完成。接下來不是馬上擴大規模，而是把這次的 spec 格式、task 拆解、驗收清單整理成可複製的模板。讓第二個問題的導入成本大幅降低。當三到五個問題跑過這個流程，團隊就建立了真正的 Agentic 交付能力——不只是個別工具使用者，而是具備整合能力的 AI 工程部門。

流程模板化第二個問題更快部門能力而非個人技能
🗺️
導入結論

新型態工作模式的核心習慣只有四個：先對齊、先規劃、訂立驗收、把關風險。這四個習慣決定了 AI 最終能幫到你多少。前三個月先求一個試點跑通，建立信心與可複製的流程，再逐步擴大。
